# VMS — Корпоративная система видеонаблюдения

Enterprise-грейд Video Management System на C#/.NET: ONVIF/RTSP-захват с GPU-декодированием,
неизменяемый (write-protected) архив с автоматическим retention, офлайн ИИ-детекция объектов
(YOLO) с поиском через Elasticsearch, REST API с ролевой моделью доступа (RBAC) и WPF-клиент
с живой сеткой камер.

Спроектирована с расчётом на 500+ камер, текущая реализация — рабочий MVP,
проверенный на **3 реальных ONVIF-камерах одновременно** (живая сетка, независимая запись
и детекция по каждой).

## Статус

Все 6 этапов реализованы и проверены вживую (не моками) на реальной камере, реальном
Elasticsearch/Postgres и реальном WPF-клиенте:

| Этап | Модуль | Что делает |
|------|--------|------------|
| M1 | `VMS.Core` | Домен, RBAC (`AccessControlManager`), аутентификация (BCrypt), append-only аудит-лог, EF Core / PostgreSQL |
| M2 | `VMS.MediaEngine` | ONVIF discovery (WS-Security), запись RTSP в сегменты через ffmpeg, авто-восстановление при обрыве связи |
| M3 | `VMS.StorageEngine` | Retention (автоудаление просроченных записей), защита от удаления через Windows ACL, вырезание клипов |
| M4 | `VMS.MetadataIndexer` | Офлайн-детекция объектов (YOLOv8 / ONNX Runtime), индексация и поиск в Elasticsearch, эмбеддинг лиц + сопоставление с известными людьми по имени, распознавание номеров (best-effort OCR), отслеживание присутствия людей с сохранением скриншотов (`PersonSightingEvent`) для отчёта «Люди в кадре» |
| M5 | `VMS.Backend.Server` | ASP.NET Core Web API (JWT), оркестрация камер из БД, REST-эндпоинты |
| M6 | `VMS.Frontend.WPF` | Desktop-клиент: логин, стартовый экран «Панель управления» (дашборд из карточек-функций — реально работают «Живой просмотр», «Архив» (просмотр по камере и дате/времени, отдельно от клипов ИИ-поиска), «Управление устройствами» (Admin+ — список/добавление/редактирование/удаление камер, плюс панель «Online Device» — находит ONVIF-камеры и NVR/DVR в локальной сети через WS-Discovery, для добавления нужны только название/логин/пароль) и, в боковой панели, «Журнал операций», остальное пока заглушки) рядом с экраном живого просмотра, живая сетка камер с переключателем раскладки (Авто/1x1/2x2/3x3/4x4) и выбором плитки кликом, отдельная кнопка на плитке для качественного потока на весь экран в отдельном окне, полностью рабочая боковая панель с деревом камер (поиск, подсветка кликом, назначение в ячейку сетки двойным кликом) и кнопки снапшота/записи/навигации по архиву на плитке, переключатель языка RU/EN/TM на весь клиент, ИИ-поиск по ключевым словам/имени/номеру с выпадающим списком результатов у поля поиска, поиск по фото с регистрацией известных людей, попап с клипом, защита файлов от удаления, живой оверлей «известен» (зелёный, с именем)/«неизвестен» (красный) на плитках Live View и Видеостены, и окно отчёта «Люди в кадре» (суммарно/известно/неизвестно по камере и дню, с переходом двойным кликом к скриншотам этого дня — каждый можно удалить по отдельности, Operator+, с подтверждением, — и кнопкой «Скачать», которая экспортирует все загруженные скриншоты в выбранную папку, разложив по подпапкам `Known/<имя>/` и `Unknown/`) |

## Архитектура

```
VMS.Core/              — домен, RBAC, аутентификация, EF Core DbContext
VMS.MediaEngine/        — ONVIF-клиент, запись потоков, снапшоты для ИИ
VMS.StorageEngine/      — retention, immutable-архив, вырезание клипов
VMS.MetadataIndexer/    — YOLO-детекция, индексация/поиск в Elasticsearch
VMS.Backend.Server/     — Worker Service + REST API (ASP.NET Core Minimal API)
VMS.Frontend.WPF/       — WPF-клиент (MVVM, LibVLCSharp)
VMS.Core.Tests/         — юнит-тесты (RBAC, аутентификация)
docker-compose.yml      — PostgreSQL + Elasticsearch для разработки
scripts/setup-tools.ps1 — разовая загрузка ffmpeg, экспорт YOLO-модели в ONNX и загрузка
                          моделей поиска по фото (каскад Хаара + SFace)
```

### Ключевые архитектурные решения

- **Захват видео**: супервизируемый процесс `ffmpeg` на камеру (не `FFmpeg.AutoGen`) — изоляция
  процессов даёт «zero-crash»: падение одной камеры не влияет на другие.
- **Живой просмотр**: `LibVLCSharp` — аппаратное декодирование «из коробки» (в т.ч. NVDEC/D3D11VA).
- **Светлая/тёмная тема**: цвета и стили WPF-клиента живут в двух параллельных словарях,
  `Themes/DarkTheme.xaml` (по умолчанию) и `Themes/LightTheme.xaml` — с абсолютно одинаковым
  набором ключей кистей/стилей, различаются только сами цвета. Переключатель ☀/🌙 в `LoginWindow`
  и в верхней панели `MainWindow` (`ThemeService.ToggleTheme`) подменяет, какой из них подключён в
  `Application.Resources` — та же техника подменяемого `ResourceDictionary`, что и переключатель
  языка ниже. В отличие от простой текстовой строки, большинство цветов темы доходят до экрана
  через объект `Style` (неявные стили по `TargetType`, собственные `ControlTemplate` у
  `ComboBox`/`DatePicker`, `Button.Style` с `BasedOn`), а не напрямую через
  `{DynamicResource}`-привязку, а WPF разрешает `BasedOn` и фиксирует `ControlTemplate` один раз —
  в момент, когда конкретный элемент был создан, — поэтому одной лишь подмены словаря недостаточно,
  чтобы перекрасить их задним числом. `App.OnThemeChanged` пересоздаёт текущее верхнеуровневое окно
  (Login или Main) на той же, всё ещё живой ViewModel сразу после подмены (без повторного входа,
  без перезагрузки камер) — исключительно чтобы его XAML заново разрешился уже против новой
  активной темы. Известное ограничение: уже открытое второстепенное окно (Архив, Управление
  пользователями, Видеостена и т. д.) сохраняет ту тему, что была активна на момент его открытия, и
  подхватывает новую только при следующем открытии.
- **Локализация (RU/EN/TM)**: подменяемый `ResourceDictionary` на язык
  (`Localization/Strings.{ru,en,tk}.xaml`), подключаемый в `Application.Resources` через
  `LocalizationService.SetLanguage` — не `.resx`/`CultureInfo`, тем потребовался бы либо
  перезапуск, либо ручная перепривязка каждого элемента, а `{DynamicResource}` обновляет всё
  дерево визуальных элементов мгновенно при смене смёрженного словаря. Переключатель RU/EN/TM
  есть и в `LoginWindow`, и в верхней панели `MainWindow`. Статусы/ошибки, собираемые в C#, идут
  через `LocalizationService.Get("Key", args...)` и показываются на языке, который был активен
  в момент формирования конкретного сообщения (без задним числом перевода уже показанного текста
  при смене языка).
- **Переключатель раскладки и выбор плитки**: одиночный клик по имени плитки выбирает её
  (оранжевая рамка-подсветка), не меняя то, что играет — отдельно от полноэкранного попапа, у
  которого теперь своя маленькая кнопка "⤢" на плитке. Тулбар над сеткой (Авто/1x1/2x2/3x3/4x4)
  задаёт фиксированную раскладку `UniformGrid` NxN; "Авто" возвращает исходное поведение
  (размер сетки по числу камер).
- **Развёрнутый просмотр одной камеры**: клик по маленькой кнопке "⤢" на плитке открывает камеру в
  качественном (main-stream) потоке в новом окне без рамки — со своим `MediaPlayer`/`VideoView`,
  а не переключением потока на уже отрисовывающемся видео-поверхности плитки сетки. Переиспользование
  уже работающего VideoView для потока другого разрешения у части камер приводило к сплошному
  белому экрану в Direct3D11-выводе без единой ошибки (сам LibVLC при этом рапортовал об успешном
  воспроизведении); новое окно/плеер на каждое открытие полностью снимает эту проблему. Окно
  позиционируется и растягивается точно на область сетки камер (не на весь экран), чтобы
  верхняя панель и боковая панель поиска оставались видны, пока камера развёрнута.
- **ONVIF**: собственный SOAP-клиент (WS-Security UsernameToken), т.к. готовые NuGet-пакеты
  по большей части заброшены.
- **Формат архива**: fragmented MP4 (`-movflags +frag_keyframe+empty_moov+...`) — без этого
  активно пишущийся сегмент нельзя прочитать (`moov atom not found`).
- **ИИ**: YOLOv8 через `YoloDotNet` (ONNX Runtime), полностью офлайн в момент инференса.
  Цвет автомобиля («red car») определяется отдельно — усреднением пикселей внутри bbox,
  т.к. в COCO нет классов цвета.
- **Аутентификация клипов**: LibVLC не умеет передавать `Authorization`-заголовок, поэтому
  эндпоинт `/api/clips/{file}` дополнительно принимает JWT через `?access_token=`
  (тот же паттерн, что и SignalR для WebSocket).
- **Безопасность сессии**: access-токен (JWT) теперь живёт недолго (30 минут) вместо токена на
  всю смену — `POST /api/auth/refresh` даёт WPF-клиенту незаметно для оператора обменять
  долгоживущий refresh-токен на новый незадолго до истечения (фоновый таймер в `ApiClient`).
  Refresh-токен одноразовый и ротируется на каждом вызове (старый отзывается, выдаётся новый), а
  в базе хранится только его SHA-256-хеш (`RefreshToken.TokenHash`) — украденный дамп БД нельзя
  переиграть в живую сессию. Отдельно `User.TokenVersion` встраивается в каждый JWT и на каждый
  запрос сверяется с текущим значением в БД (`Program.cs`, `OnTokenValidated`) — понижение роли,
  деактивация пользователя или сброс пароля администратором увеличивают это значение, так что
  изменение действует с самого следующего запроса, а не только после естественного истечения
  срока уже выданного токена.
- **Устойчивость к падению сервера**: дочерние процессы ffmpeg привязаны к Windows Job Object
  с флагом kill-on-close — если backend умирает любым способом (краш, `Stop-Process -Force`,
  диспетчер задач), ffmpeg-процессы камер убиваются ОС автоматически, не остаются
  «осиротевшими» и не занимают лимит одновременных RTSP-подключений камеры.
- **Устойчивость WPF-клиента**: необработанное исключение на UI-потоке (например, сбой у
  конкретной камеры) показывает окно с ошибкой и пишет `crash.log`, но не убивает всё
  приложение целиком.

## Требования

- .NET SDK 10
- Inno Setup 6 — только для сборки офлайн-установщика (см. ниже)
- Docker (для PostgreSQL и Elasticsearch)
- Python 3.11+ с `pip` (для разового экспорта YOLO-модели в ONNX)
- Windows (WPF-клиент, Windows ACL для immutable-архива)
- NVIDIA GPU — опционально, для аппаратного декодирования/CUDA

## Быстрый старт

```powershell
# 1. Поднять инфраструктуру
docker compose up -d

# 2. Один раз скачать ffmpeg, экспортировать YOLO-модель, скачать модели
#    для поиска по фото (каскад Хаара + эмбеддер SFace) и языковые данные
#    Tesseract (для распознавания номеров, best-effort)
.\scripts\setup-tools.ps1

# 3. Применить миграции БД
dotnet ef database update --project VMS.Core --startup-project VMS.Core

# 4. Настроить тестовую камеру (гитигнорится, не коммитится)
#    Создать VMS.Backend.Server/appsettings.local.json:
#    {
#      "Vms": {
#        "TestCamera": {
#          "CameraId": "cam-01",
#          "IpAddress": "192.168.1.50",
#          "OnvifPort": 80,
#          "Username": "admin",
#          "Password": "..."
#        }
#      }
#    }

# 5. Запустить сервер
dotnet run --project VMS.Backend.Server --urls http://localhost:5080

# 6. Запустить WPF-клиент
dotnet run --project VMS.Frontend.WPF
```

При первом запуске сервер сам создаст пользователя `superadmin` и выведет
одноразовый пароль в лог — им и логинимся в WPF-клиенте.

## Офлайн-установщик для другого ПК

Всё выше — это режим разработки (Docker, `dotnet run`). Для установки на обычный компьютер
есть один файл `dist\VMS-Full-Setup.exe`, который ставит систему целиком и не требует на
целевом ПК ни интернета, ни .NET, ни Java, ни Docker, ни каких-либо инструментов
разработчика.

### Что он устанавливает

| Компонент | Куда | Служба Windows |
| --- | --- | --- |
| Бэкенд (REST API + запись + детекция) | `C:\Program Files\Turkmentelekom VMS\backend` | `VMSBackend`, автозапуск |
| WPF-клиент | `C:\Program Files\Turkmentelekom VMS\frontend` | — (ярлык в меню «Пуск» и на рабочем столе) |
| PostgreSQL 16 | `C:\Program Files\PostgreSQL\16` | `VMS-Postgres`, автозапуск |
| Elasticsearch 9 (один узел) | `C:\ProgramData\VMS\elasticsearch` | `elasticsearch-service-x64`, автозапуск |
| ffmpeg, модели YOLO/SFace/Haar, tessdata | `C:\Program Files\Turkmentelekom VMS\{tools,models,tessdata}` | — |
| Архив, клипы, снимки, HLS, e-maps, индекс ES | `C:\ProgramData\VMS\` | — |

Данные намеренно лежат не в `Program Files`: видеоархив там не место, а служебная обёртка
Elasticsearch (procrun) ненадёжно работает, когда в пути к `ES_HOME` есть пробелы.

Порты подбираются автоматически — первый свободный из `5080/5081/5082` для API,
`5432/5434/5435` для PostgreSQL, `9200/9201/9202` для Elasticsearch, — поэтому установка не
конфликтует с уже имеющимися на ПК PostgreSQL или Elasticsearch. Выбранные порты, пароль БД и
ключ подписи JWT генерируются при установке и сохраняются в
`C:\ProgramData\VMS\config\secrets.json` (доступ только у SYSTEM и администраторов).
Elasticsearch и API слушают только `127.0.0.1`.

Ключи, которыми шифруются пароли камер (ASP.NET Data Protection), установщик кладёт в
`C:\ProgramData\VMS\dp-keys` и защищает DPAPI на уровне машины — это новая опция
`Vms:DataProtectionKeysPath`. Без неё связка ключей по умолчанию привязана к профилю
пользователя: служба (LocalSystem) и запуск того же exe из консоли под администратором получили
бы разные ключи, и консольный запуск не смог бы расшифровать пароли камер, записанные службой.
В режиме разработки опция пустая — поведение остаётся прежним.

### Требования к целевому ПК

- Windows 10 / 11, x64
- права администратора (установка служб)
- ≥ 12 ГБ свободного места на системном диске (проверяется перед установкой), плюс запас под
  видеоархив
- ≥ 8 ГБ ОЗУ (Elasticsearch берёт 1 ГБ heap)
- интернет **не нужен**

### Первый вход

Установщик один раз запускает бэкенд, чтобы применить миграции и создать пользователя
`superadmin`, и сохраняет его одноразовый пароль в файл `VMS-superadmin-parol.txt` на рабочем
столе (и в `C:\ProgramData\VMS\`). Пароль показывается только один раз — смените его сразу
после первого входа. Полный лог установки: `C:\ProgramData\VMS\logs\install.log`.

### Сборка установщика (на машине разработчика)

```powershell
# 1. Разово: Inno Setup 6 (https://jrsoftware.org/isdl.php) и scripts\setup-tools.ps1

# 2. Разово: скачать два сторонних дистрибутива в installer\downloads\
#    (~860 МБ, в git не коммитятся). Команды с докачкой:
.\scripts\build-installer.ps1 -ShowDownloadUrls

# 3. Собрать (публикация обоих приложений + упаковка, 10–25 минут)
.\scripts\build-installer.ps1
```

На выходе — `dist\VMS-Full-Setup.exe` (~1.2–1.4 ГБ). Его и копируют на целевой ПК (запуск от
имени администратора). `ISCC.exe` вручную запускать не нужно: payload сначала надо собрать, это
и делает скрипт. `-SkipPublish` переиспользует уже собранный `installer\payload` — только для
правок самого `.iss` или скриптов установки.

Сборочный скрипт специально удаляет из опубликованного бэкенда `appsettings.local.json`:
`dotnet publish` копирует его в вывод (файл попадает под стандартный glob `appsettings*.json`),
а на машине разработчика в нём лежат реальные логин и пароль камеры — в установщик они попасть
не должны.

### Повторная установка и удаление

Установщик можно запускать повторно поверх существующей установки: он остановит службу, обновит
файлы, переиспользует `secrets.json` и **не тронет** существующую базу и архив.
`install.ps1` можно запустить и вручную, если установка оборвалась:

```powershell
powershell -ExecutionPolicy Bypass -File "C:\Program Files\Turkmentelekom VMS\scripts\install.ps1" -AppDir "C:\Program Files\Turkmentelekom VMS"
```

Удаление (через «Параметры → Приложения») снимает службу `VMSBackend` и останавливает
PostgreSQL и Elasticsearch, переводя их в ручной запуск, но **данные не удаляет** — ни
`C:\ProgramData\VMS`, ни базу `vms`. Потеря видеоархива при обычном удалении была бы худшим
сюрпризом, чем оставшаяся папка, а сохранённые данные означают, что повторная установка
подхватит прежний архив. Инструкция по полной очистке остаётся в файле
`VMS-UDALENIE-OSTALNOGO.txt` на рабочем столе.

### Адрес сервера у клиента

Клиент по умолчанию обращается к `http://localhost:5080`. Чтобы указать другой адрес (например,
поставить клиент на рабочее место оператора, а сервер держать на отдельной машине), создайте
рядом с `VMS.Frontend.WPF.exe` файл `vms-client.json`:

```json
{ "BackendBaseAddress": "http://192.168.1.10:5080" }
```

Установщик пишет этот файл сам — с тем портом, который фактически достался API. Файл читается
из каталога исполняемого файла, а не из рабочего каталога: ярлык запускает `.exe` с произвольным
рабочим каталогом.

### Бэкап на установленном ПК

`scripts/backup-database.ps1` рассчитан на окружение разработчика и вызывает `pg_dump` через
`docker exec`. На установленном ПК база нативная, поэтому дамп делается напрямую:

```powershell
$env:PGPASSWORD = (Get-Content 'C:\ProgramData\VMS\config\secrets.json' | ConvertFrom-Json).VmsDbPassword
```

## Роли (RBAC)

`Guard < Viewer < Operator < Admin < SuperAdmin` — единая логика (`AccessControlManager`)
используется и на сервере, и в WPF-клиенте (для скрытия недоступных элементов UI), так что
поведение никогда не расходится. `Guard` в перечислении `UserRole` имеет значение `-1`, а не
остальные роли перенумерованы вверх: Role хранится как обычное целое число в БД, поэтому
добавление ниже существующих значений сохраняет смысл уже сохранённых строк пользователей
ровно таким же, каким он был раньше.

- **Guard** — только просмотр живого видео (`Permission.ViewLiveStream`) — без поиска, архива
  и экспорта. Роль для человека у монитора, который просто наблюдает за камерами, а не ведёт
  расследование по записям.
- **Viewer** — + просмотр архива, поиск
- **Operator** — + вырезание клипов, поиск по архиву по загруженному фото, регистрация/удаление
  известных людей (`/api/known-persons`) — всё на ступень выше обычного поиска, поскольку
  отслеживает или называет конкретного человека
- **Admin** — + управление камерами, удаление обычных файлов архива, защита файла результата
  поиска от удаления (кнопка «Защитить» в WPF-клиенте рядом с результатом поиска), запуск
  пересчёта эмбеддингов лиц, управление учётными записями (`/api/users`, экран «Управление
  пользователями» в WPF) вплоть до роли Admin включительно — создание/изменение/удаление
  учётной записи SuperAdmin требует, чтобы сам вызывающий уже был SuperAdmin
- **SuperAdmin** — + удаление защищённых (immutable) файлов архива, управление учётными
  записями SuperAdmin.

Помимо пяти ролей выше, экран WPF «Добавить/изменить пользователя» также показывает список всех
отдельных функций (Просмотр вживую, Архив, Поиск, Поиск по фото, Распознавание лиц, Экспорт
клипов, Управление камерами, Политика хранения, Удаление файлов архива, Настройка системы,
Управление пользователями) — так Admin+ может выдать пользователю одну конкретную функцию, не
повышая его на весь уровень целиком — например, Viewer, которому дополнительно разрешён поиск по
фото, но который не становится полноценным Operator. Это чисто аддитивно: можно только добавить
поверх того, что уже даёт Role, но никогда не отнять, и вызывающий может выдать только ту функцию,
которой обладает сам (Operator не может выдать «Управление камерами» никому, поскольку у него самого
её нет) — это обеспечивается и списком чекбоксов (функции, которых нет у вызывающего, вообще не
показываются как варианты), и повторно на сервере в `POST`/`PUT /api/users`
(`UserEndpoints.TryResolveAdditionalPermissions`), так что это невозможно обойти прямым вызовом
API. Одно исключение: удаление защищённых (immutable) файлов архива нельзя выдать таким способом
никогда, даже SuperAdmin'у — это остаётся привязано только к иерархии Role
(`AccessControlManager.NonGrantablePermissions`), без аддитивной лазейки для самого разрушительного
права в системе.

  «Управление пользователями» также не даёт разжаловать, деактивировать
  или удалить свою же учётную запись, а также последнего оставшегося активного SuperAdmin —
  единственный экран, где неосторожный клик мог бы иначе заблокировать доступ всем
  администраторам

## Эксплуатация

- **Бэкапы базы данных**: `scripts/backup-database.ps1` делает дамп PostgreSQL (пользователи,
  RBAC, аудит-лог, конфиги камер, известные люди, группы камер, раскладки видеостены,
  refresh-токены — всё, кроме индекса Elasticsearch и файлов архива/клипов/снапшотов на диске) в
  timestamped plain-SQL файл в `backups/` (в .gitignore — в дампе есть хеши паролей), с хранением
  последних 14 по умолчанию. Рассчитан на запуск по расписанию (Windows Task Scheduler).
  Восстановление:
  ```powershell
  docker exec -i vms-postgres psql -U vms -d vms < backups/vms_<timestamp>.sql
  ```
- **Документация API**: Swagger UI доступен на `/swagger`, когда сервер запущен в окружении
  `Development` (`ASPNETCORE_ENVIRONMENT=Development`, значение по умолчанию у `dotnet run`) — в
  продакшене не включается, поскольку это API для операторов/админов, а не публичное.

## Известные ограничения текущего MVP

- CUDA execution provider для YOLO не установлен — детекция работает на CPU. Сама видеокарта
  есть и драйвер готов (проверено через `nvidia-smi`); проблема именно в том, что
  `Microsoft.ML.OnnxRuntime.Gpu.{Windows,Linux}` (~200-240 МБ каждый, тянется транзитивно через
  `YoloDotNet.ExecutionProvider.Cuda`) не восстанавливается с nuget.org в этой сети —
  `dotnet add package` раз за разом падает на середине обоих файлов с «response ended
  prematurely», это подтвердилось и при повторной попытке. `YoloDotNetDetector` уже принимает
  флаг `useCuda` и разветвляется по нему, пока что — только чтобы залогировать предупреждение и
  уйти на CPU; заменить эту ветку на настоящий `CudaExecutionProvider` — несколько строк, как
  только пакет реально восстановится в другой сети; больше ничего в пайплайне менять не нужно
  (`IObjectDetector` — единственный контракт, от которого зависят вызывающие).
- В списке результатов поиска WPF-клиента теперь есть и «Защитить», и «Удалить» рядом с каждым
  результатом (`DeleteArchiveFileCommand`, видна при `Session.CanDeleteStandardArchive` — Admin+;
  для защищённого файла всё равно нужен SuperAdmin, это проверяется на сервере так же, как в API)
  — удаление идёт с подтверждением, по той же схеме, что и удаление отдельного скриншота в
  галерее «Люди в кадре».
- Нижняя панель Live View: «Остановить все», «Снимок», «Ручная запись», «Пауза/Воспроизведение» и
  «Развернуть на весь экран» работают (действуют на выбранную плитку, кроме «Остановить все» —
  та останавливает все сразу); снимок сохраняется в `Изображения\VMS Snapshots`, запись — в
  `Видео\VMS Recordings`. Кнопки шага по фрагментам архива (⏮/⏭) — по-прежнему только заготовка
  интерфейса (`IsEnabled="False"`); боковая панель с деревом камер (поиск, подсветка кликом,
  назначение в ячейку сетки двойным кликом) полностью работает, как и выпадающий список
  размера сетки (Авто, 1×1..8×8 — заменил прежний ряд кнопок фиксированных размеров).
  Иконки слева: управление группами камер (именованный, упорядоченный набор камер —
  например «камеры 1-5» одна группа, «6-20» другая — `/api/camera-groups`), быстрое
  переключение на сохранённую группу или «все камеры» (применяется к сетке в раскладке
  Авто), и переключатель, фильтрующий сетку до камер с недавней (последние 5 минут)
  неподтверждённой тревогой — «тревога» здесь означает детекцию человека без совпадения
  с зарегистрированным именем, либо любую детекцию транспорта (в системе нет реестра
  «известный/неизвестный транспорт» кроме номера, поэтому честно считаем тревожным любое
  транспортное средство, а не придумываем несуществующий признак). Ярлык на Архив/Playback,
  который раньше был на этой иконке, по-прежнему доступен через карточку Playback на
  Панели управления.
- Видеостена (`/api/video-wall-layouts`) на выбранном мониторе открывается либо в режиме
  «Зеркало Живого просмотра» (старое поведение — полноэкранная копия текущей сетки Live View),
  либо как именованная сохранённая раскладка: сетка «строки x столбцы», где каждая ячейка
  закреплена за одной камерой и может иметь свой размер за счёт объединения соседних ячеек
  (как объединение ячеек в Excel) в редакторе раскладок (открывается кнопкой «Управление
  раскладками…» в окне видеостены). Объединение поглощает только один целый соседний
  прямоугольник той же высоты/ширины за раз — без Г-образных/частичных объединений — а смена
  числа строк/столбцов у раскладки, в которой уже есть ячейки, сбрасывает всю сетку обратно к
  простым ячейкам 1x1 (с диалогом подтверждения), теряя все объединения и назначенные камеры.
- Распознавание номера (`plateNumber`, доступно через `GET /api/search?q=...`) не использует
  отдельную модель детектора номера — область номера внутри рамки YOLO для автомобиля ищется
  простой эвристикой по контурам, а распознаётся тем, что нашлось, через Tesseract OCR. Это
  заметно менее точно, чем настоящий ANPR-пайплайн: ожидаются частые промахи и искажённые
  результаты, особенно под углом, ночью или на маленьком/далёком автомобиле. Считайте поиск по
  номеру «показывает вероятных кандидатов», а не надёжным точным совпадением.
- Сопоставление известных людей (`POST /api/known-persons`, помечает будущие детекции «person»
  именем) наследует все ограничения точности поиска по фото выше (каскад Хаара + SFace, без
  выравнивания по ключевым точкам) и добавляет своё: сравнение идёт по фиксированному порогу
  косинусного сходства (0.363, опубликованный SFace порог «то же лицо») со всеми
  зарегистрированными фото. Теперь перед вычислением эмбеддинга лицо выравнивается: второй
  каскад Хаара (`haarcascade_eye.xml`) находит оба глаза и поворачивает вырезанное лицо так,
  чтобы линия глаз была горизонтальной (`OnnxFaceEmbedder.AlignByEyes`) — более дешёвое
  2-точечное выравнивание, чем полные 5-точечные ориентиры YuNet, но оно напрямую исправляет
  наклон головы — главный реальный источник расхождения эмбеддингов для фронтальной
  CCTV-камеры; если два правдоподобных глаза не найдены (профиль, очки, низкое разрешение),
  используется невыровненный вырез. Само сравнение по-прежнему использует фиксированный порог
  косинусного сходства (0.363, опубликованный SFace порог «то же лицо»), но теперь также
  требует, чтобы лучший результат превосходил второе место по разнице (0.05) — это уменьшает
  число случаев, когда два похожих зарегистрированных человека путаются на почти равном счёте,
  ценой того, что иногда система вернёт «нет совпадения» вместо неуверенной догадки.
  Регистрация одного и того же имени несколько раз с разными фото уже работает (каждая
  регистрация — отдельная строка `KnownPerson`; сравнение берёт лучший результат по имени) —
  диалог регистрации в WPF теперь прямо это подсказывает, поскольку несовпадение из-за
  фото регистрации под углом было главным реальным пробелом в точности.
- Отчёт «Люди в кадре» (считать каждого увиденного человека + сохранять скриншот,
  `PersonPresenceTracker`) считает *новый трек*, а не уникального физического человека — это тот
  же алгоритм сопоставления ближайших центроидов между последовательными AI-снимками (не
  непрерывное видео), что и линия пересечения в People Counting, без какого-либо распознавания
  по внешности — только позиция. `MaxMissedFrames` (сколько подряд пропущенных снимков трек
  переживает, прежде чем повторное появление засчитывается как новый) настроен на 6 — это
  ~30 секунд при 5-секундном шаге снимков — что заметно снижает самый частый ложный повтор
  (человек ненадолго вышел из кадра) по сравнению с прежним значением 2 (~10с), но это компромисс,
  а не починка: слишком щедрое окно рискует слить двух *разных* людей в один трек. Сам отчёт
  делает один запрос к Elasticsearch на камеру на день, а не одну
  агрегацию (тот же подход, что уже используется в `GetPeopleCountAsync`) — это нормально для
  небольшого числа камер за обычный период, но становится медленным при многих камерах и
  длинном диапазоне дат. Живой оверлей «известен/неизвестен» на сетке опрашивает сервер раз в
  ~1.5с на каждую видимую плитку — это визуальная подсказка, а не защищённый канал распознавания.
- Проверено на 3 камерах одновременно (живая сетка 2×2, независимая запись/детекция) —
  компоненты спроектированы для многокамерности (process-per-camera, конфигурируемые
  retention-политики на камеру), но нагрузочного тестирования на десятках/сотнях камер
  не проводилось.
- Поиск по фото (`POST /api/search/by-face`) использует каскад Хаара для поиска лица и
  SFace (ONNX, opencv_zoo) для эмбеддинга — без выравнивания лица по 5 ключевым точкам
  (для этого нужен более новый детектор YuNet, который OpenCvSharp пока не оборачивает),
  поэтому совпадения заметно менее надёжны для лиц в профиль/под углом, чем в полном
  пайплайне YuNet+SFace.
- Экран Playback (просмотр архива по камере/дате/времени + встроенная панель ИИ-поиска:
  вкладки «По имени» / «По атрибутам» / «По фото», визуальная сетка результатов и дневной
  таймлайн с фиолетовыми/жёлтыми метками совпадений людей/транспорта) грузит запись
  фиксированными окнами по 15 минут через тот же `POST /api/clips`, что и попап клипа из
  ИИ-поиска — нет настоящего ползунка перемотки, только кнопки «◀ 15 мин» / «15 мин ▶» по
  шагам (двойной клик по карточке результата поиска сразу переносит воспроизведение в этот
  момент), и на каждый шаг заново извлекается кусок (`ffmpeg -c copy`, быстро, но не
  мгновенно), а не потоково отдаётся сырой файл сегмента. Скорость воспроизведения
  (1x/2x/4x/16x), покадровый шаг (на паузе) и снимок кадра в файл — настоящие команды LibVLC,
  а не заглушки.
- Вкладка «По атрибутам» намеренно предлагает только те фильтры, которые реально умеет
  распознавать пайплайн детекции: тип объекта, цвет, номер и имя зарегистрированного
  человека. Пол, возраст, очки/маска и подтип транспорта (седан/внедорожник и т.д.) не
  предлагаются вовсе — YOLO и цветовой тэггер не умеют это классифицировать, а серый
  недоступный элемент управления вводил бы в заблуждение насчёт возможностей системы. По
  той же причине на таймлайне отмечаются только совпадения людей и транспорта
  (фиолетовый/жёлтый); отдельного сигнала «движение» для красной метки нет — в этой системе
  сама детекция и есть сигнал движения.
- Эмбеддинг лица появляется у детекции «person» только если внутри её рамки реально нашлось
  лицо — человек спиной к камере или слишком мелкий/размытый в кадре детектируется как
  «person» (находится по этому слову), но не находится по фото.
- Редактирование камеры (`PUT /api/cameras/{code}`) всегда перезапускает её пайплайн
  захвата/ONVIF — даже смена одного только имени вызывает несколько секунд простоя именно
  этой камеры, т.к. нет логики сравнения изменившихся полей. `Code` камеры неизменяем после
  создания; чтобы его сменить — удалить камеру и добавить заново (архивные файлы и записи
  в Elasticsearch привязаны к `Code`, а не к внутреннему `Id` базы данных, так что это безопасно).
- ONVIF WS-Discovery (`GET /api/cameras/discover`) находит устройства только в той же
  L2/broadcast-сети, что и сервер — не может найти устройства за пределами локальной сети
  (стандартное ограничение multicast, не баг). Также предполагает, что device service
  устройства находится по стандартному пути `/onvif/device_service`, а число каналов
  устройства становится известно только после подключения с верными логином/паролем — сам
  Probe не может заранее сказать, обычная это IP-камера или многоканальный NVR/DVR. Каждый
  канал NVR/DVR добавляется отдельной независимой строкой `Camera` (тот же IP, разный код) —
  объединения каналов в общую "родительскую" карточку в UI нет.
- У детекций, проиндексированных до появления поиска по фото, эмбеддинга нет, пока не
  запущен `POST /api/admin/backfill-face-embeddings` (Admin+, без кнопки в UI — запускать
  вручную); он заново достаёт кадр из архивного видео на каждую детекцию, поэтому не может
  восстановить эмбеддинг для детекций, чей архивный сегмент retention-политика уже удалила.
- Только Windows — осознанно, не по недосмотру: `VMS.Frontend.WPF` — WPF-приложение, а
  защита от удаления в `ImmutableArchiveManager` построена на Windows ACL
  (`FileSystemAccessRule`) — ни у того, ни у другого нет эквивалента под Linux/macOS в этом
  коде. Перенос десктоп-клиента на кросс-платформенный UI-фреймворк и замена механизма
  неизменяемости на что-то вроде immutable-флагов файловой системы или lock-политик
  объектового хранилища — оба это отдельные, большие переписывания, а не смена конфига.
- Elasticsearch теперь настоящий кластер из 3 нод (`vms-es01`/`02`/`03` в `docker-compose.yml`,
  `cluster.name: vms-cluster`), а не single-node — у индекса детекций по умолчанию 1 реплика,
  размещённая на другой ноде, чем primary, так что кластер продолжает отдавать поиск/запись при
  падении любой одной ноды (проверено: `GET /_cat/shards/vms-object-events` показывает primary и
  реплику на двух разных нодах, статус кластера `green`). Все три ноды пока крутятся на одной
  физической машине (в реальном деплое каждую — на свой хост) — это настоящий кластер, но пока не
  по-настоящему *распределённый*. У PostgreSQL до сих пор нет потоковой репликации, но есть
  point-in-time recovery через `scripts/backup-database.ps1` (см. «Эксплуатация» выше) —
  у индекса детекций Elasticsearch автоматического снапшота всё ещё нет (на практике он
  рассматривается как перестраиваемый поисковый кэш, а не система хранения записей, поскольку
  детекции в принципе восстановимы из архива через ИИ-пайплайн, просто не быстро).
- `Dockerfile` (в корне репо) собирает `VMS.Backend.Server` в Windows-образ контейнера
  (`mcr.microsoft.com/dotnet/aspnet:10.0-nanoserver-ltsc2022`) — Linux-образ бы собрался, но
  упал бы при первом же обращении к архиву, поскольку `ImmutableArchiveManager` вызывает
  Windows-only ACL API. Требует Docker Desktop в режиме «Windows containers», который не может
  работать одновременно с собственным `docker-compose.yml` этого репо (обычные Linux-контейнеры
  для Postgres/Elasticsearch) — именно поэтому собрать его в этой же dev-среде не проверено;
  воспринимайте его как честный первый черновик, а не проверенный образ. У `VMS.Frontend.WPF`
  Dockerfile нет и не планируется — это интерактивное десктоп-приложение, а не сервис.

## Тесты

```powershell
dotnet test VMS.Core.Tests           # RBAC, аутентификация
dotnet test VMS.Backend.Server.Tests # шифрование паролей камер, генерация refresh-токенов, claims в JWT, дедупликация в presence tracker
```

Прогоняется на каждый push/PR в `main` через GitHub Actions (`.github/workflows/ci.yml`) — см.
бейдж CI в начале этого README. Покрытие осознанно узкое: чистая логика в `VMS.Core` и
`VMS.Backend.Server`, которую можно тестировать без реальной инфраструктуры. `VMS.MediaEngine`
(реальные процессы ffmpeg, реальные RTSP-потоки), `VMS.MetadataIndexer` (реальные ONNX-модели) и
`VMS.Frontend.WPF` (реальный UI) проверяются ручной end-to-end верификацией на реальном железе
(см. раздел «Статус») — ни один из этих трёх не ложится в быстрый детерминированный юнит-тест, а
нестабильный интеграционный тест, зависящий от живой камеры или загруженной ML-модели, был бы
хуже, чем отсутствие автотеста вообще.
